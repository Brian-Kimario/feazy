# A3.2 — Operations recovery: design, dry run, rollback

Status: **design and transactional dry run only. Nothing here is applied to the shared database.**
Migration (unapplied): `supabase/migrations/20261030_106_admin_reconcile_job.sql`
Dry run: `supabase/dry-runs/20261030_106_admin_reconcile_job.dryrun.sql` (generated by `gen_106.py`),
report: `…dryrun.report.json`.

## 1. What this slice delivers, and what it deliberately does not

| Exception (A3.1) | Recovery in A3.2 | Why |
|---|---|---|
| Booking cancelled, job still `assigned` | **New** `admin_reconcile_job` (migration 106) | Only unambiguous drift is auto-repairable |
| Any live job needing a human decision (overdue offer, no-show, stuck, stale quote, unmatched with a job) | **Existing** `admin_cancel_job` (A2) | Already canonical, audited, notifies |
| Unmatched / stale booking with **no job** (`c779c0d4`) | **None yet.** Blocked on `transition_booking_state` | No second booking state machine (decision) |
| Expired booking that still needs service | Customer-consented reschedule: **design only** (§4.2) | Never retried through the matcher |
| Professional verification | Existing verification state machine (A1) | Not a job recovery |
| Booking/job drift where the booking is still pending/confirmed but the job is cancelled (5 live rows) | **None.** Needs `transition_booking_state` | See §3 |

Findings that shaped the scope:

1. **A "retry matching" action is not needed and was not built.** `process_assignment_queue` already re-offers
   every `pending` booking with a future start and no job (or an unassigned `assigned` job) every minute. An
   admin retry would be a duplicate of the cron, and for a past-start booking `_offer_next` treats the pool as
   empty by design. Owner revision A is satisfied by *not* adding a path to the matcher at all.
2. **Cancelled-booking jobs are invisible to the matcher** (`booking_status = 'pending'` is required), so the
   two orphan jobs would stay in the queue forever without a repair.
3. **The WhatsApp trigger fires on any `to_state = 'cancelled'` event** (`on_job_state_transition` queues a
   `cancellation` row). A bookkeeping reconciliation must not message a customer about a cancellation they
   already know about, so the migration makes that trigger skip `admin_reconcile` events.
4. **Lock order.** `_offer_next` locks booking then job; `admin_cancel_job` locks job then booking (existing,
   A2). Two concurrent runs could deadlock (one is aborted by Postgres; no corruption). The new function uses
   the matcher's order. Proposal: align `admin_cancel_job` in the same release (not changed here).

## 2. Authorization design (owner revision C)

`admin_reconcile_job(p_job_id, p_expected_state, p_reason)` — `SECURITY DEFINER`, `search_path = public`,
`EXECUTE` granted to `authenticated` and `service_role`, revoked from `PUBLIC`/`anon`.

Independent checks inside the function, in order, before any write:

1. `auth.uid()` present, else `42501`.
2. `profiles.role = 'admin'` for that uid, else `42501`.
3. Input validation (job and expected state required, reason 5–500 chars after trim), else `22023`.
4. Job exists, else `P0002`.
5. Lock **booking, then job** (`FOR UPDATE`); re-read both under the lock.
6. Expected state equals the locked state, else `{ok:false, code:'STALE_STATE'}` (covers duplicates).
7. Booking is `cancelled`, job is `assigned`, no `paid` payment, else `{ok:false, code:'NOT_ELIGIBLE'}`.

Only then does it set the existing `app.admin_cancel_job` hand-off and call `transition_job_state`. The GUC is
not the authority: `transition_job_state` still re-verifies the admin role itself, and the flag is set only
after every check above and cleared immediately after. `transition_job_state` is **not modified**; a direct
admin call to it is still refused (dry run c18). Refusals return a typed result and write nothing.

App layer (planned, not built): `runAdminAction` (guard → Zod → `.requested` audit, fail closed → execute →
`.succeeded`/`.failed`) calling the RPC through the user-scoped client, so `auth.uid()` is the admin. Never
the service-role client for this RPC.

## 3. Valid booking/job combinations (owner revision B)

`booking_status` is vestigial: only `create_booking` (`pending`) and `admin_cancel_job` write it. Live data:

| booking + job | Count (live) | Class | Treatment |
|---|---|---|---|
| pending/confirmed + no job | 1 pending | expected → **recoverable** once start has passed | `c779c0d4`: blocked on booking transition |
| pending/confirmed + assigned…quote_pending | 1 (in_progress) | expected (status not maintained) | none |
| pending/confirmed + completed/closed | 3 | expected (status not maintained) | none |
| pending/confirmed + **cancelled** job | 5 | **historical drift**, harmless to the matcher | not repaired; needs `transition_booking_state` |
| cancelled + no job / cancelled / closed | 3 | expected terminal | none |
| cancelled + **assigned** | 2 (the fixtures) | **confirmed defect, auto-repairable** | `admin_reconcile_job` |
| cancelled + accepted/on_the_way/arrived | 0 | confirmed defect, **manual** | `admin_cancel_job` (notifies) |
| cancelled + in_progress/quote_pending | 0 | confirmed defect, **never automatic** | investigate; work may be under way |
| completed + not completed/closed | 0 | confirmed defect, **never automatic** | investigate; never overwrite |

Never overwritten automatically: completed, closed, paid (any `paid` payment), in-progress, quote-pending.

## 4. Recovery contracts

Common to all DB-backed recoveries: actor is an authenticated admin; Zod-validated input
`{id, expectedState, reason}`; canonical transition only; row locks; stale expected state rejected; typed
result; app-level `.requested/.succeeded/.failed` audit; **payments are never refunded, captured, recharged
or modified** (a captured payment is surfaced and blocks automatic repair).

### 4.1 State mismatch — cancelled booking, live job  → `admin_reconcile_job`
- **Preconditions** booking `cancelled`; job `assigned`; expected state matches; no `paid` payment.
- **Input** `{jobId, expectedState: 'assigned', reason(5–500)}`.
- **State changes** job `assigned → cancelled` via `transition_job_state` (event `admin_reconcile`);
  `offer_expires_at` cleared if an offer was held; booking untouched (already cancelled).
- **Related records** `admin_reconciliations` row (internal reason, admin read only); if an offer was held,
  a `withdrawn/job_cancelled` row in `booking_assignment_attempts`.
- **Notifications** customer: none (booking already cancelled; WhatsApp queue suppressed). Professional: only
  if they held an offer, neutral text, in-app.
- **Payments** counted for eligibility only; a `paid` one refuses the repair; a `pending` one is untouched.
- **Concurrency** booking→job `FOR UPDATE`; expected-state recheck; a duplicate gets `STALE_STATE`.
- **Failure** typed `STALE_STATE`/`NOT_ELIGIBLE`; exceptions only for auth/validation; atomic.
- **Tests** dry run c01–c21 (§8).

### 4.2 Unmatched / stale pending
- **Booking has a job** (unassigned or offered): `admin_cancel_job` (exists).
- **No job** (`c779c0d4`): canonical cancellation of a booking needs `transition_booking_state`, which does
  not exist in this database (also the cause of the customer `cancelBooking` P1). **Not built here.**
  Do not touch `c779c0d4` until that lands.
- **Reschedule with customer consent** (design): admin proposes a new window → customer notification with
  accept/decline → on accept, a *new* start time is written through the booking transition and only then does
  the matcher see it (it already requires `scheduled_start > now()`); on decline or no answer, cancel. The
  matcher is never invoked for an expired booking. Needs a consent table; propose in A3.3 after owner review.
- Preconditions for any retry (if ever): still schedulable, no terminal job, no active offer, offer limits met.

### 4.3 Overdue offer / stale pending job / potential no-show / stuck in-progress / stale quote-pending
- Existing `admin_cancel_job` (A2): job in a non-terminal state, expected state matches, customer-safe
  reason category plus private internal reason, customer and professional notified, offer withdrawn, booking
  cancelled, payment review flagged. Reassignment is A4 (not here). A no-show report does not auto-cancel.
- Overdue offers are normally cleared by the cron; an overdue row means the cron is failing, which the
  Operations health strip already reports.

### 4.4 Professional verification
Unchanged (A1 state machine, `approve/reject` with expected status and audit). Not a job recovery.

## 5. State-transition analysis

New transitions introduced: **none**. `admin_reconcile_job` performs `assigned → cancelled`, already valid in
`transition_job_state` (`assigned → accepted|cancelled`). It writes no booking transition (booking already
`cancelled`). The only widened behavior is three function bodies; `transition_job_state` and the
`jobs_professional_required` constraint are unchanged (A2 already allows a NULL professional when cancelled).

## 6. Compatibility assessment

Migration changes three existing objects and adds two:
- `on_job_state_transition`: adds an early return for `event_type = 'admin_reconcile'`. Every other event is
  identical. Dry run c19/c20: admin cancel and ordinary professional cancel still queue exactly one WhatsApp
  row and notify the customer with the same kind as before.
- `_notify_for_event`: adds one mapping and one branch; other branches byte-for-byte as in migration 105.
- New: `admin_reconciliations` (RLS on, admin SELECT only, no writes granted), `admin_reconcile_job`.
- No RLS policy is loosened; no existing grant changes; no existing row is modified at apply time.
- Apply is data-neutral: the two fixtures remain unreconciled until an admin runs the action.

## 7. Defects kept visible alongside this slice

- **P1, before A4:** customer `cancelBooking` calls missing `transition_booking_state` and `booking_events`.
  This is also the root cause class of the fixtures' drift. Proposed fix: a real `transition_booking_state`
  (single booking state machine) plus a customer cancel that cancels job and booking in one transaction.
- Historical drift: 5 rows with a pending/confirmed booking and a cancelled job (§3).
- Verification document integrity: `_verification_missing_documents` counts any non-rejected `id` row without
  checking the storage object; the synthetic pro.a row has no object. Fix before real professionals:
  record → storage object exists → reviewable → authorised approval → eligible.
- A1 approve/reject browser journeys unverified; Playwright blocked.
- Open: legacy verified professionals with 0 documents; neutralising old migration 20261004_003; support-role
  reads; customer notification on mid-job suspension; dropping `under_review`; professionals can still cancel
  their own job; `admin_cancel_job` lock order (§1.4).

## 8. Dry-run results (rolled back; live database verified unchanged afterwards)

Method: one transaction on the shared DB, `BEGIN` + the migration + a `DO` block, every case in its own
sub-transaction that is rolled back, and the block finishes by `RAISE EXCEPTION 'DRYRUN_REPORT …'` so the
whole transaction aborts by construction. Callers are impersonated with `request.jwt.claims` and
`SET LOCAL ROLE`. Fixtures: the two preserved orphan jobs, plus synthetic payments and states created inside
the rolled-back transaction. Post-run check: function and table absent, both fixtures unchanged, zero
synthetic payments, zero `admin_reconcile` events.

| Case | Result |
|---|---|
| c01 unauthenticated / c02 `anon` role | `42501` Not authenticated / permission denied |
| c03 customer / c04 professional | `42501` Only administrators |
| c05 short reason / c07 null state | `22023` |
| c06 unknown job | `P0002` |
| c08 stale expected state | `STALE_STATE`, nothing written |
| c09 booking not cancelled | `NOT_ELIGIBLE`, unchanged |
| c10 accepted / c11 in_progress / c12 completed | `NOT_ELIGIBLE`, unchanged |
| c13 captured payment | `NOT_ELIGIBLE`, payment and job unchanged |
| c14 happy path | job `cancelled`; 1 `admin_reconcile` event; 1 record; booking unchanged; **0** in-app and **0** WhatsApp notifications; no `admin_job_cancellations` row |
| c15 duplicate request | second call `STALE_STATE`; still exactly 1 event and 1 record |
| c16 outstanding offer | withdrawn attempt recorded, offer cleared, professional notified once, customer 0 |
| c17 pending payment | preserved exactly |
| c18 admin direct `transition_job_state` | still refused |
| c19 `admin_cancel_job` regression | works; customer kind `job_cancelled_by_admin`; 1 WhatsApp row |
| c20 professional cancel regression | customer kind `job_cancelled`; 1 WhatsApp row |
| c21 both fixtures reconciled | mismatch count 2 → 0 (both leave the Operations queue) |

**Not covered, stated honestly:** true two-session concurrency. Creating the objects in two concurrent
rolled-back transactions would block on the catalog, so it can't isolate row-lock behaviour. Coverage is the
lock-order analysis, the `FOR UPDATE` re-read, and the sequential duplicate (c15). Re-test with two sessions
immediately after apply, on the fixtures, before enabling the UI. Not covered: app-layer Zod/audit wiring
(not built), browser journeys, Playwright.

## 9. Rollback plan

Before apply: snapshot `pg_get_functiondef` of `on_job_state_transition` and `_notify_for_event` (the 105/live
bodies are reproduced in the migration comments and git history).
- **Not yet used (no rows reconciled):** one transaction — `DROP FUNCTION admin_reconcile_job(uuid,text,text)`;
  `CREATE OR REPLACE` the two functions from the snapshot; `DROP TABLE admin_reconciliations`. No data effect.
- **After use:** reconciled jobs stay `cancelled` (correct, and each has its `admin_reconcile` event and
  record). Do not drop `admin_reconciliations` then; restore the two functions and revoke EXECUTE on
  `admin_reconcile_job` instead. Reversing a reconciliation itself would mean re-opening a job for a cancelled
  booking, which is never wanted.
